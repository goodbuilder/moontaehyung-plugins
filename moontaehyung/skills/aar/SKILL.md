# After Action Review

## Process
1. Establish the reviewed scope, intended outcomes, acceptance criteria, and relevant constraints from the request and existing records. Do not invent an earlier baseline with hindsight.
2. Compare expectations with observed outcomes using deliverables, logs, decisions, and participant accounts. Distinguish evidence, recollection, and uncertainty.
3. Examine both strengths and shortcomings: what happened, why, what to sustain, and what to change. Avoid turning every shortcoming into a claimed root cause. Return a need for RCA to the coordinator only if an important unresolved causal question could change the review's conclusions and deeper investigation is within the user's scope. Respect an explicit AAR-only request; already established causes need no repeat investigation.
4. Convert lessons into specific actions with an owner or accountable role, application date or next-work trigger, and an observable check. Mark unassigned commitments explicitly.
5. Distinguish proposed actions, completed actions, and verified improvements. Reuse existing action IDs and evidence rather than opening duplicate records.

## Output contract
For a small review, present the following directly in chat. When a file is needed, default to a Markdown report in the user's requested location or the current task output directory. Respect an explicitly requested format.

Use [references/report-template.md](references/report-template.md). Evaluate both the result and the process: a good outcome alone does not prove the method was sound. Identify contemporaneous expectations versus honestly reconstructed ones. Preserve differing accounts instead of inventing consensus. Give each lesson its applicable conditions, prioritize the smallest useful set of actions, and identify when they will be revisited.

The linked template owns the comparison and action-table fields; do not maintain a second competing schema. Action types include sustain and change. Preserve successful practices even if there were no failures. Keep the report proportional; a successful small task need not produce a long report.

## Completion
Distinguish report completeness from action readiness: unassigned actions or missing decisive evidence make follow-up readiness partial. An AAR report does not mean its actions have been implemented. Do not implement process or configuration changes solely because the review recommends them. For ambiguous routing or multiple methods, use an available analysis-router without repeating its comparisons.
